### How to reproduce?

It's hard to reproduce - It happens rarely when I try to write big parquet files. After calling WriteColumnAsync, I get ```ArgumentOutOfRangeException``` - see full error below.
Seems that in [IronCompress\Iron.cs](https://github.com/aloneguid/ironcompress/blob/master/managed/IronCompress/Iron.cs), the returned output variable "len" is negative, which is then used to initialize an array, and as a result causing the ```ArgumentOutOfRangeException```.

```
bool ok = Native.compress(
                           compressOrDecompress,
                           (int)codec, inputPtr, input.Length, null, &len, level);
```



This is probably because the ```snappy::RawCompress```, called in [api.cpp](https://github.com/aloneguid/ironcompress/blob/master/native/api.cpp), has an integer overflow. [Here's a bug](https://github.com/xerial/snappy-java/security/advisories/GHSA-fjpj-2g6w-x25r) on Snappy about it, which has already been fixed.

I assume the solution would be to upgrade the Snappy version, but I'm not sure if it would just return a more informative error.

IronCompress is already on latest snappy version, but there is a bug in narrowing data type as you have mentioned. Thanks for reporting this, I'll try to reproduce and get some fixes in.

In the meantime, you can try to write in batches (row groups) as it looks like columns are massive anyway and readers will have issues decompressing them if ram is an issue.

### siggemannen on 2025-07-07

I got hit with this too, although my strings aren't larger than 200 chars, but the data is quite big.
The problem is likely that he uses `int` and not `size_t` in https://github.com/aloneguid/ironcompress/blob/bdba797f44b1bddc25cb421f7371128925fe686e/native/api.cpp#L42

int is signed while size_t is unsigned, and can hold more than int.
