## Description

### Issue description

**Background**
I'm working to run the `Floor` executable on Raspberry Pi OS without requiring .NET runtimes or C library compatibility workarounds. Two new builds (or either one of these two) would improve compatibility immensely:

1. glibc-linked build (instead of musl-linked) targeting Raspberry Pi OS (e.g. Arm32/Arm64).
- Current releases include Windows, macOS, and Linux x64, but not Raspberry Pi.
- Raspberry Pi OS uses glibc (instead of musl), so a glibc-linked build would "just work."

2. Fully-static musl build for Arm64
- No dynamic dependencies avoid the musl/glibc pain
- (From my limited research: Use `musl‑gcc -static` or NativeAOT + `-static` to produce self-contained binaries.)

**Proposed changes**
- CI / GitHub Actions enhancements:
  - Cross-compile and publish `Floor` for Arm32/Arm64 targeting glibc.
  - Provide static Arm64 builds using musl-gcc or NativeAOT + `-static`

- Artifact naming suggestion:
  - floor-linux-glibc-arm32.zip
  - floor-linux-glibc-arm64.zip
  - floor-linux-static-arm64.zip

**Motivation**
- **User friendliness**: Native glibc builds run on Raspberry Pi OS without extra setup.  Targeting of the Raspberry Pi platform is mentioned in the [README.md](https://github.com/aloneguid/parquet-dotnet?tab=readme-ov-file#apache-parquet-for-net), but setting up the `Floor` reference implementation binary is proving very problematic because of the musl/glibc dynamic library mismatch.  (Especially for the inexperienced Linux users that tend to gravitate to the Pi, like me!)
- **Reliability**: Static binaries prevent runtime library issues.
- **Precedent**: In my limited research, .NET NativeAOT supports static musl binaries, and many cross‑platform CLI tools (e.g., Azure IoT/azddns) ship static binaries with CI support.
